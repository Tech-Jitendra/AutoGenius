# AutoGenius — Database Design (PostgreSQL)

Naming: `snake_case` tables/columns. Primary keys are UUIDs. Timestamps are `timestamptz`.
Migrations are managed with the API's migration tooling (introduced with the Auth task).

## Entity Relationship Summary

```
users 1─∞ vehicles 1─∞ service_records
                       1─∞ maintenance_reminders
users 1─∞ ai_conversations 1─∞ ai_messages
users 1─∞ quotations 1─∞ quotation_items
```

`service_records` and `maintenance_reminders` are implemented (Task 04). The tables
further down (`expenses`, `ai_*`, `quotations`) are the V1 design and are built in
Tasks 05–07.

### refresh_tokens

Refresh credentials are stored only as SHA-256 hashes of the presented token;
the plaintext token exists only on the client. Rotation marks the old row
revoked and points it at its replacement; presenting a revoked hash revokes
every session of that user (reuse detection).

| Column          | Type          | Notes                    |
| --------------- | ------------- | ------------------------ |
| id              | uuid PK       |                          |
| user_id         | uuid FK→users | CASCADE on delete; INDEX |
| token_hash      | varchar(64)   | sha256 hex; UNIQUE       |
| expires_at      | timestamptz   |                          |
| revoked_at      | timestamptz   | nullable                 |
| replaced_by_id  | uuid          | nullable; rotation chain |
| created_at      | timestamptz   |                          |

UNIQUE INDEX: `(token_hash)`. INDEX: `(user_id)`.

### vehicles

Every read and write is scoped by `user_id` as well as the vehicle id, so a foreign
vehicle is indistinguishable from a missing one. The application takes a `FOR UPDATE`
lock on the owner's `users` row for the whole transaction, which makes "the first
vehicle is the default" and "promote this vehicle" deterministic; the partial unique
index below is the backstop if that ever breaks.

| Column              | Type         | Notes                          |
| ------------------- | ------------ | ------------------------------ |
| id                  | uuid PK      | generated by the API           |
| user_id             | uuid FK→users| NOT NULL; INDEX; CASCADE on delete |
| make                | varchar(50)  | NOT NULL                       |
| model               | varchar(50)  | NOT NULL                       |
| variant             | varchar(50)  | nullable                       |
| registration_number | varchar(20)  | nullable; stored normalised to upper case |
| manufacturing_year  | int          | NOT NULL; CHECK 1900…2100      |
| fuel_type           | varchar(20)  | NOT NULL; CHECK PETROL/DIESEL/CNG/HYBRID/ELECTRIC |
| transmission        | varchar(20)  | NOT NULL; CHECK MANUAL/AUTOMATIC/AMT/CVT |
| purchase_date       | date         | nullable; date-only so no timezone shift |
| current_odometer    | integer      | nullable; CHECK 0…2000000      |
| is_default          | boolean      | NOT NULL DEFAULT false         |
| created_at          | timestamptz  |                                |
| updated_at          | timestamptz  |                                |

INDEX: `(user_id)`, `(user_id, created_at DESC)`.
UNIQUE: `(id, user_id)` — added by the Task 04 migration so history rows can point at
(vehicle, owner) as one unit.
UNIQUE INDEX: `(user_id) WHERE is_default` — at most one default per user.
UNIQUE INDEX: `(user_id, regexp_replace(upper(registration_number), '[^A-Z0-9]', '', 'g'))
WHERE registration_number IS NOT NULL` — plates are unique per owner, compared on a
canonical key that ignores case and separators (`MH 12 AB 1234` and `mh-12-ab-1234` are
one plate), while the row keeps the readable stored value. Vehicles without a plate never
collide.

`fuel_type` and `transmission` are `varchar` + CHECK rather than PostgreSQL enum types so
that adding a value is a data change, not a `TYPE` migration.

### service_records

One workshop visit. Written only through the service-history endpoints, always under a
vehicle the caller owns.

| Column          | Type           | Notes |
| --------------- | -------------- | ----- |
| id              | uuid PK        | generated by the API |
| vehicle_id      | uuid           | NOT NULL |
| user_id         | uuid           | NOT NULL; FK→users CASCADE |
| service_date    | date           | NOT NULL; date-only so no timezone shift; the API rejects future dates |
| odometer_km     | int            | nullable; CHECK 0…2 000 000 |
| workshop_name   | varchar(120)   | nullable |
| service_type    | varchar(30)    | NOT NULL; CHECK on the shared `SERVICE_TYPES` list |
| description     | text           | nullable — the work performed |
| parts_replaced  | jsonb          | NOT NULL DEFAULT `'[]'`; CHECK `jsonb_typeof = 'array'` |
| labour_cost     | numeric(12,2)  | NOT NULL DEFAULT 0; CHECK ≥ 0 |
| parts_cost      | numeric(12,2)  | NOT NULL DEFAULT 0; CHECK ≥ 0 |
| other_cost      | numeric(12,2)  | NOT NULL DEFAULT 0; CHECK ≥ 0 |
| total_cost      | numeric(12,2)  | NOT NULL DEFAULT 0; CHECK `= labour + parts + other` |
| notes           | text           | nullable |
| created_at      | timestamptz    | |
| updated_at      | timestamptz    | |

`CONSTRAINT service_records_vehicle_owner_fkey FOREIGN KEY (vehicle_id, user_id)
REFERENCES vehicles (id, user_id) ON DELETE RESTRICT` — the composite key is why a row
cannot claim a vehicle that belongs to someone else; the database rejects it even if the
application forgets to check. It needs `UNIQUE (id, user_id)` on `vehicles`, which the
same migration adds.

INDEX: `(vehicle_id, service_date DESC, created_at DESC)` for the newest-first list,
`(vehicle_id, service_type, service_date DESC)` for the type filter, `(user_id)`.

**Why `parts_replaced` is JSONB, not a child table.** A part line on a bill is a note
about one visit: it is never queried on its own, never joined, never updated in place, and
never carries a total that the rest of the schema aggregates over. A
`service_record_parts` table would mean a second write per record, its own ownership
checks, and a delete cascade, to store data that is always read as part of the record.
The cost roll-ups deliberately live in the three `*_cost` columns (and are enforced by
`total_cost`), so a report never has to unpack JSON. Each element is
`{ "name": string, "quantity": number|null, "cost": number|null }` — validated by the
shared Zod schema (at most 100 lines per record, `name` required and ≤ 120 chars, quantity
1…9999, cost non-negative) before it reaches the column, because a CHECK constraint cannot
validate JSON shape.

**Money is `numeric(12,2)`, never float.** Paise must add up exactly: `total_cost` is both
a CHECK constraint and the sum behind expenditure reports. The API recomputes the total in
whole cents on every write, so a client-supplied total is ignored.

**Two rules live in Zod, not in CHECK constraints**: "service date is not in the future"
and "completion date is not in the future". PostgreSQL only allows IMMUTABLE expressions
in a CHECK, and `CURRENT_DATE` is not immutable.

### maintenance_reminders

A promise to do work later. Either a due date, a due odometer reading, or both.

| Column                     | Type         | Notes |
| -------------------------- | ------------ | ----- |
| id                         | uuid PK      | |
| vehicle_id                 | uuid         | NOT NULL |
| user_id                    | uuid         | NOT NULL; FK→users CASCADE |
| title                      | varchar(120) | NOT NULL |
| description                | text         | nullable |
| due_date                   | date         | nullable |
| due_odometer_km            | int          | nullable; CHECK 0…2 000 000 |
| interval_months            | int          | nullable; CHECK 1…120 |
| interval_km                | int          | nullable; CHECK 1…2 000 000 |
| last_completed_date        | date         | nullable |
| last_completed_odometer_km | int          | nullable; CHECK 0…2 000 000 |
| status                     | varchar(20)  | NOT NULL DEFAULT 'ACTIVE'; CHECK ACTIVE/COMPLETED/DISMISSED |
| created_at / updated_at    | timestamptz  | |

CHECK `due_date IS NOT NULL OR due_odometer_km IS NOT NULL` — a reminder with neither
could never become due, so it would be dead weight in the list. Intervals are never zero:
a zero interval would complete and instantly fall due again at the same reading.
Same composite `(vehicle_id, user_id)` RESTRICT foreign key as `service_records`.

INDEX: `(vehicle_id, status)`, `(user_id)`, `(due_date)`, `(status, due_date)`.

**Urgency is not stored.** `OVERDUE` / `UPCOMING` / `SCHEDULED` is computed on every read
from `due_date`, `due_odometer_km`, the vehicle's `current_odometer` and today, so it can
never go stale overnight. Day arithmetic is done on `YYYY-MM-DD` calendar days and
`Date.UTC`, which makes the boundary timezone-independent: the same due date reads the
same way in Mumbai and Seattle. `COMPLETED` and `DISMISSED` reminders have no urgency at
all (`alertStatus: null`), so closed work can never appear as overdue.

**Deleting a vehicle does not cascade to history.** Both foreign keys are `RESTRICT`, and
`DELETE /vehicles/:id` first counts the rows and answers `409` with what is still attached
("This vehicle still has 3 service records and 2 maintenance reminders. Delete those
first…"). A vehicle with no history deletes exactly as before. Users are the one exception:
`user_id → users.id` is `CASCADE`, because an account removal should take everything with
it, and no endpoint deletes a user.
